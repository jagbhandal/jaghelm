# SLO: jaghelm-dashboard-feed — feed success rate

- **slo_id:** `slo-jaghelm-dashboard-feed-request-success-rate`
- **Service:** `jaghelm-dashboard-feed`
- **Owner:** jagbhandal
- **Review cadence:** quarterly
- **Error budget policy:** [`error-budget-policy.md`](error-budget-policy.md)

## User journey

A user opens the dashboard. The SPA calls `GET /api/services`
(`server/routes/services.js`), which serves the unified node + container +
monitor payload from the warm in-memory cache, falling back to an on-demand
refresh on a cold start. **Success** = the user gets their dashboard data
(HTTP 2xx). **Failure** = a `5xx`, or the `503 "Service data not yet available"`
cold-start path when even the inline refresh returns nothing.

## SLI

- **Type:** request-success-rate
- **Numerator:** `sum(rate(http_requests_total{route="/api/services",method="GET",code!~"5.."}[window]))`
- **Denominator:** `sum(rate(http_requests_total{route="/api/services",method="GET"}[window]))`
- **Labels:** `route=/api/services`, `method=GET`
- **Good/bad boundary:** `304 Not Modified` (ETag revalidation, see
  `cache.jsonWithEtag`) counts as **good** — the client got a valid answer.
  Only `5xx` and the `503` cold-start failure count as bad. `4xx` from the auth
  middleware (a logged-out client) is **excluded** from the denominator — it's a
  client-side state, not a JagHelm reliability failure.

## Target

- **Target:** 99.5% over 28 days
- **Error budget:** 201.6 minutes per 28-day window (0.5% of requests may fail)

### Why this target (not 99.9%+)

- The endpoint is a read from an in-memory `Map`, so the *intrinsic* failure rate
  is near zero — the failures that do occur are (a) cold starts right after a
  container restart, and (b) the rare case where every configured node is
  unreachable at refresh time. 99.5% leaves headroom for a deploy/restart or two
  per window without burning the whole budget.
- 99.9%+ would be **false precision** for a single-instance, single-maintainer
  app with no redundancy: one unlucky restart during a scrape and the month is
  blown. `slo_review.py` flags `target_too_high` at ≥99.99% for exactly this
  reason.

## Multi-window burn-rate alerts

Per Google SRE Workbook ch. 5 (two windows: a long window for signal, a short
window to confirm the burn is still happening — kills both flapping and stale
alerts). Generated by `error_budget_calculator.py --target 99.5 --window-days 28`.

| Alert | Severity | Long / short window | Burn rate | Budget consumed | Meaning |
|---|---|---|---|---|---|
| fast_burn | page | 1h / 5m | 13.44 | 2% in 1h | feed is on fire (restart loop / crash) |
| slow_burn | page | 6h / 30m | 5.6 | 5% in 6h | sustained degradation |
| ticket_burn | ticket | 3d / 6h | 0.933 | 10% in 3d | trending bad, look this week |

```promql
# fast_burn (page) — 2% of budget in 1h
(
  sli:rate1h > 13.44 * (1 - 0.995)
  AND
  sli:rate5m > 13.44 * (1 - 0.995)
)

# slow_burn (page) — 5% of budget in 6h
(
  sli:rate6h > 5.6 * (1 - 0.995)
  AND
  sli:rate30m > 5.6 * (1 - 0.995)
)

# ticket_burn (ticket) — 10% of budget in 3d
(
  sli:rate3d > 0.933 * (1 - 0.995)
  AND
  sli:rate6h > 0.933 * (1 - 0.995)
)
```

`sli:rateXX` is a recording rule = `bad_requests / total_requests` over window
`XX` for this SLI. For a one-user homelab, "page" realistically means an
ntfy/Gotify push (JagHelm already integrates both) rather than a pager.

## Instrumentation required (not yet present)

JagHelm exports no HTTP metrics today. To make this SLI measurable, add an
Express middleware (around the route mount in `server/index.js`) that increments
`http_requests_total{route,method,code}` and observes
`http_request_duration_seconds`, exposed on a `/metrics` endpoint Prometheus
scrapes. See [`README.md`](README.md) → "Prerequisite".
