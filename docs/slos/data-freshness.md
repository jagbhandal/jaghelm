# SLO: jaghelm-data-freshness

- **slo_id:** `slo-jaghelm-data-freshness`
- **Service:** `jaghelm-data-freshness`
- **Owner:** jagbhandal
- **Review cadence:** quarterly
- **Error budget policy:** [`error-budget-policy.md`](error-budget-policy.md)

## User journey

JagHelm's whole pitch is **"live data, not just links"** — the numbers on the
dashboard must be *current*, not a frozen snapshot from when the refresh loop
last worked. The background loop (`server/refresh.js`, default every 30 s) keeps
the `services` cache warm; routes serve from it (TTL 120 s in `server/cache.js`).

**Good** = the data served is younger than the 120 s cache TTL (i.e. the refresh
loop ran recently). **Bad** = the served `services` payload is ≥120 s old — the
refresh loop has stalled, crashed, or every cycle is failing, and the user is
looking at stale numbers without knowing it. This is the SLO that catches the
silent-death failure mode the other two don't: the HTTP endpoint can keep
returning fast 2xx responses while serving hours-old data.

## SLI

- **Type:** data-freshness
- **Freshness threshold:** 120 s (the cache TTL — older than this is, by the
  app's own definition in `cache.js`, a stale read)
- **Numerator:** `sum_over_time((jaghelm_cache_age_seconds{cache="services"} < 120)[window])`
- **Denominator:** `count_over_time(jaghelm_cache_age_seconds{cache="services"}[window])`
- **Labels:** `cache=services`, `freshness_threshold=120s`

Measured by sampling the age of the `services` cache entry
(`Date.now() - entry.ts`) on each Prometheus scrape and counting the fraction of
samples under 120 s.

### Why 120 s and the `services` cache specifically

- 120 s is the existing `CACHE_TTL_MS` — past it, the route stops trusting the
  entry, so it's the app's own freshness contract. The refresh interval is 30 s,
  so a healthy loop keeps age well under 120 s; crossing it means **≥4
  consecutive refresh cycles were skipped or failed**, which is a real stall.
- `cache="services"` is the panel the user stares at (nodes, containers, monitor
  health). The same SLI can later be cloned for `ups`, `gitea`, `integrations`
  with their own labels, but `services` is the load-bearing one.
- **Important nuance:** the background loop skips a cycle if the previous one
  hasn't finished (`bgRefreshRunning` guard in `refresh.js`). Under a chronically
  slow upstream the cache can legitimately age out. That is *exactly* the
  user-visible staleness this SLO should catch — it is not a false positive.

## Target

- **Target:** 99.5% of samples fresh (<120 s) over 28 days
- **Error budget:** 201.6 minutes-equivalent per window (0.5% of samples may be stale)

### Why this target

Restarts and the occasional long refresh cycle will briefly age the cache; 99.5%
tolerates that — a healthy 30 s loop spends almost all of its time well under the
120 s threshold, so 0.5% of stale samples is generous headroom. A loop that has
actually died will sit at 0% fresh and blow through the budget within hours —
which is the point. Don't set this to 99.9%: normal container restarts plus a
slow Prometheus during a backup window would generate noise without indicating a
real problem. Don't drop to 99.0% either — that's the reviewer's "probably wrong
SLI" floor and would let the cache be stale ~7 h/month before anyone is told.

## Multi-window burn-rate alerts

Generated by `error_budget_calculator.py --target 99.5 --window-days 28`.

| Alert | Severity | Long / short window | Burn rate | Budget consumed | Meaning |
|---|---|---|---|---|---|
| fast_burn | page | 1h / 5m | 13.44 | 2% in 1h | refresh loop is dead *right now* |
| slow_burn | page | 6h / 30m | 5.6 | 5% in 6h | loop failing for most cycles |
| ticket_burn | ticket | 3d / 6h | 0.933 | 10% in 3d | intermittent staleness, investigate |

```promql
# fast_burn (page) — loop has stalled
(
  sli:rate1h > 13.44 * (1 - 0.995)
  AND
  sli:rate5m > 13.44 * (1 - 0.995)
)

# slow_burn (page)
(
  sli:rate6h > 5.6 * (1 - 0.995)
  AND
  sli:rate30m > 5.6 * (1 - 0.995)
)

# ticket_burn (ticket)
(
  sli:rate3d > 0.933 * (1 - 0.995)
  AND
  sli:rate6h > 0.933 * (1 - 0.995)
)
```

`sli:rateXX` = fraction of stale samples (`age ≥ 120s`) over window `XX`.

## Instrumentation required (not yet present)

Add a `jaghelm_cache_age_seconds{cache}` gauge, computed from the cache `ts` in
`server/cache.js` at scrape time, on the `/metrics` endpoint. This is the
cheapest of the three to instrument and arguably the highest-value for a homelab
dashboard — it's the alert that tells you the dashboard went quietly stale.
