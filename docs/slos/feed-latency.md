# SLO: jaghelm-dashboard-feed — feed latency

- **slo_id:** `slo-jaghelm-dashboard-feed-request-latency`
- **Service:** `jaghelm-dashboard-feed`
- **Owner:** jagbhandal
- **Review cadence:** quarterly
- **Error budget policy:** [`error-budget-policy.md`](error-budget-policy.md)

## User journey

The dashboard should *feel* live. When the SPA polls `GET /api/services`, the
response is served from the warm in-memory cache and should come back fast enough
that cards render without a visible stall. **Good** = response within the latency
threshold. **Bad** = slower than the threshold (a cold-start inline refresh, a
slow `services.yaml` reload, or GC pause).

## SLI

- **Type:** request-latency
- **Threshold:** 300 ms (server-side response time for `GET /api/services`)
- **Numerator:** `sum(rate(http_request_duration_seconds_bucket{route="/api/services",method="GET",le="0.3"}[window]))`
- **Denominator:** `sum(rate(http_request_duration_seconds_count{route="/api/services",method="GET"}[window]))`
- **Labels:** `route=/api/services`, `threshold=300ms`

### Why 300 ms and why a cache-warm endpoint

The cache hit path is `getCached()` + `JSON.stringify` + an MD5 ETag hash
(`cache.js`) — sub-millisecond for a typical payload. The 300 ms threshold is
generous *on purpose*: it absorbs cold-start inline refreshes (which fan out to
Prometheus/cAdvisor/Kuma) and a node or two being slow, while still catching a
real regression (e.g. someone makes the route block on a synchronous disk read).
The SLO is on **server response time**, not browser paint — JagHelm controls the
former, not the user's network or device.

## Target

- **Target:** 99.5% of requests under 300 ms over 28 days
- **Error budget:** 201.6 minutes-equivalent per window (0.5% of requests may be slow)

### Why this target (not higher, not lower)

Cold starts are unavoidable: every container restart serves the first
`/api/services` from an inline refresh that *does* hit upstreams and can exceed
300 ms. Those are legitimately "slow but correct" responses. 99.5% leaves room
for restarts and the occasional slow upstream without burning budget, while still
flagging a systematic latency regression. Going **lower** (99.0%) sits on the
reviewer's "probably wrong SLI" floor and tolerates too many slow responses for
an endpoint that's a sub-millisecond cache read on the happy path. Going **higher**
(99.9%+) would mostly measure upstream latency JagHelm can't control — re-check
at the quarterly review once real percentile data exists.

## Multi-window burn-rate alerts

Generated by `error_budget_calculator.py --target 99.5 --window-days 28`.

| Alert | Severity | Long / short window | Burn rate | Budget consumed |
|---|---|---|---|---|
| fast_burn | page | 1h / 5m | 13.44 | 2% in 1h |
| slow_burn | page | 6h / 30m | 5.6 | 5% in 6h |
| ticket_burn | ticket | 3d / 6h | 0.933 | 10% in 3d |

```promql
# fast_burn (page)
(
  sli:rate1h > 13.44 * (1 - 0.995)
  AND
  sli:rate5m > 13.44 * (1 - 0.995)
)

# slow_burn (page)
(
  sli:rate6h > 5.6 * (1 - 0.995)
  AND
  sli:rate30m > 5.6 * (1 - 0.995)
)

# ticket_burn (ticket)
(
  sli:rate3d > 0.933 * (1 - 0.995)
  AND
  sli:rate6h > 0.933 * (1 - 0.995)
)
```

Here `sli:rateXX` = `slow_requests / total_requests` (fraction over threshold)
over window `XX`.

## Instrumentation required (not yet present)

Needs `http_request_duration_seconds` as a Prometheus **histogram** with an `le`
bucket boundary at `0.3` (and a few neighbours, e.g. 0.1 / 0.3 / 1 / 3, so the
threshold can be re-tuned without re-instrumenting). Same middleware as the
feed-success SLO. See [`README.md`](README.md) → "Prerequisite".
